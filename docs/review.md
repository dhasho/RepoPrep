# 代码审查

审查代码时，以目标分支上的实际 diff、当前 head commit、真实调用路径和可复核证据为依据，只报告有证据且由本次 diff 引入或暴露的问题；与本次变更无关的问题另行记录，不混入本次阻断项。普通小改动在提交前同样按此核对；是否启用云端 review 及其权限范围以平台状态为准。

不为凑数量编造 finding；没有实质缺陷时明确写“未发现需处理的问题”，并给出实际验证范围。实际执行的命令、结果与环境条件如实记录；未执行或失败的检查如实说明，不把 mock 或 smoke 结果描述成真实服务验收。检查命令以 [`validation.md`](validation.md) 和 `package.json` 中实际存在的 npm scripts 为准。新提交改变了受影响代码时，重跑相关检查并重新确认相关结论；不把旧 head 的结论当作新 head 的审查结果。

## 严重度

严重度描述问题的影响，不替代验收标准判断；不是 P0/P1 但造成核心验收标准未满足的问题，同样必须在合并前修复或按明确流程重新界定范围。

- **P0 — 紧急**：广泛不可用、敏感信息广泛泄漏或数据广泛损坏，无需特定场景即可触发。立即处理。
- **P1 — 严重**：通过特定但可达的路径破坏主要用户流程、关键数据完整性或安全边界（含敏感信息泄漏）。合并前修复并验证。
- **P2 — 一般缺陷**：具体、可复现并影响用户或输出正确性。默认本次修复；明确接受风险时记录理由、影响与后续去向。
- **P3 — 改进建议**：可读性、维护性或体验提升，不构成当前功能缺陷，可另行记录跟进。

定级看触发条件和实际影响，不看改动行数或语气：小范围但可泄漏凭证的问题仍是 P1；无具体用户后果的偏好建议通常是 P3。

## RepoPrep 重点路径

结合改动范围检查以下边界，不要求逐项打勾：

- renderer → preload → IPC guard → service 的来源校验、运行时 schema 与项目授权；不凭 TypeScript 类型推断运行时输入可信。
- 扫描/快照/脱敏 → 上下文构建 → 模型请求 → 解析与配额 → 持久化 → UI/Markdown 导出的数据链路；核对失败、截断、重试和部分结果。
- 取消、重复启动、迟到进度事件、项目切换和监听器清理；确认状态更新不会落到错误项目或已结束操作。
- 边界输入和 Windows 路径：空目录、忽略规则、路径分隔符、权限失败、超大/异常内容及用户可控配置。
- 用户承诺的题量、界面文案、`shared/types.ts` 中预算与 README 是否一致；共享契约变化沿实际调用者检查。
- 模型错误与凭证处理：错误消息、日志、事件、结果文件和导出内容不泄漏 API Key 或其他敏感信息。

只陈述被审查 commit 的实际实现和验证能够证明的保证；涉及持久化加密、原子写入、操作隔离等属性时，先从代码路径和验证证据确认，再描述为已有保证。

## 外部 review 意见处理

收到外部 review、自动化 finding 或用户转述的审查意见时，先对照本地代码和真实调用路径，逐条归类为**成立、部分成立、不成立或重复**并简述证据；不直接照搬 reviewer 提出的方案，先确认根因、责任边界、兼容性与最小可行修复，再选择范围内最合理的处理。

成立或部分成立的问题修复并补充针对根因的回归证据；不采纳全部或部分建议时，说明理由与剩余风险。明确未解决的问题保持可见状态和后续去向，不静默 resolve 或写成已修复；被接受风险的 P2 持续可见，直到后续事项完成或风险被重新评估。
