# 代码审查与外部反馈

本文规定 RepoPrep 的作者自检、独立审查和外部 review 闭环。云端功能在 Codex/GitHub 连接配置中启用，仓库文档与模板提供规则；是否启用及权限范围以平台状态为准。GitHub 配置步骤见 [GitHub Review 配置](github-review-setup.md)。

按 [协作入口](../AGENTS.md) 区分改动范围：重大改动通过 PR 执行独立审查；普通小改动完成相应自检后直接 commit、push，不要求 Issue、PR 或形式化审批。下文合并与批准状态的规定适用于 PR；直接提交仍须核对实际 diff、受影响路径及验证证据。

## 审查目标与证据

审查以目标分支上的实际 diff、当前 head commit、真实调用路径和可复核证据为依据。只报告有证据且由本次 diff 引入或暴露的问题。发现既有且与本次变更无关的问题时，另列为后续 issue 建议，不把它混入本次阻断项。

不要为了让审查显得完整而编造 finding。没有实质缺陷时可以明确写“未发现需处理的问题”，并给出实际验证范围。审查结论是对明确版本组合的判断；新提交可能改变代码、上下文或验证结果，因此必须针对新 head 重新确认受影响的结论。

审查时记录：

- 被审查的 head commit，以及目标 base 分支和用于比较的 base commit。
- 实际查看的 diff 范围、受影响模块和调用路径。
- 实际执行的命令、结果与环境条件；未执行或失败的检查要如实说明。
- 结论成立所依赖的证据，以及 mock、smoke、手工步骤或环境限制留下的边界。

PR 每次更新后都应重新核对变更 head 与 base。若新增提交改变了受影响代码，应重跑相关检查并重新确认相关 finding；不得把旧 head 的批准直接当作新 head 的审查结果。版本必须高于目标分支，具体规则见 [版本管理](VERSIONING.md)。

## 作者自检与独立审查

作者先对照任务或 issue 的验收标准和 [项目规范](project-standards.md) 自检，说明改了什么、为何这样改、验证了什么以及尚未覆盖什么。检查命令以 [验证指南](validation.md) 和 `package.json` 中实际定义的 npm scripts 为准；不要把未运行的命令写成通过，也不要把 mock 结果描述成真实服务验收。

合并前由独立主代理审查实际 diff 和真实运行路径。作者自检与独立审查是两个职责，不能用同一段自述替代独立审查。审查者应从任务入口追踪数据与权限边界，核对具体证据，并检查版本与目标分支的关系。

审查状态的含义：

- **Approve**：当前 head/base 上没有尚未处理的阻断问题，验收标准有足够证据支持。
- **Request changes**：存在必须在合并前处理的问题，包括任何影响核心验收标准的缺口。
- **Comment**：提供不阻断的建议、边界说明或需跟踪事项；它本身不表示批准。

GitHub 显示 `COMMENTED`、没有 review、机器人没有发现问题或单项检查通过，都不等于批准。合并判断必须基于本规则所需的独立审查与验收证据。

## 严重度和处理

严重度描述问题的影响，不替代验收标准判断。即使某项不是 P0/P1，只要它造成核心验收标准未满足，也必须在合并前修复或按明确的验收变更流程重新界定范围；不能因标签较低而忽略。

- **P0 — 紧急**：造成广泛不可用、敏感信息广泛泄漏或数据广泛损坏，且无需特定场景即可触发。立即处理，暂停合并。
- **P1 — 严重**：通过特定但可达的路径破坏主要用户流程、关键数据完整性或安全边界，包括敏感信息泄漏。合并前修复并验证。
- **P2 — 一般缺陷**：具体、可复现并影响用户或输出正确性的缺陷。默认在本次修复；若明确接受风险，需记录理由、影响、责任人或后续 issue 与计划。
- **P3 — 改进建议**：可读性、维护性或体验提升，不构成当前功能缺陷。可作为非阻断建议或另建 issue。

严重度应说明触发条件和实际影响，不按改动行数或主观语气定级。小范围但可泄漏凭证的问题仍可能是 P1；未影响验收且无具体用户后果的偏好建议通常是 P3。

## Finding 格式

每条 finding 应落在具体代码行上，引用审查时的 head commit，并提供足以独立复核的信息：

```text
[P1] 标题应描述可执行的修复目标
位置：path/to/file.ts:123（Reviewed commit: <head>）
条件：什么输入、状态或操作会触发。
机制：沿真实调用路径说明错误如何发生；指出 diff 引入或暴露的环节。
影响：用户、数据、安全或验收标准会受到什么影响。
修复方向：给出边界内最小且可行的修正方向，不预设唯一实现。
验证：应覆盖的回归证据或命令。
```

Finding 标题使用 `[P0]` 至 `[P3]` 前缀和可执行描述。位置应尽量指向 diff 中能解释问题的行；代码行会变化时，commit 标识用于固定上下文。避免只说“可能有问题”或直接贴一套未经核实的重写方案。

## RepoPrep 的重点路径

结合改动范围检查以下边界；不要求每个 PR 机械地逐项打勾：

- renderer → preload → IPC guard → service 的来源校验、运行时 schema 与项目授权；不要仅凭 TypeScript 类型推断运行时输入可信。
- 扫描/快照/脱敏 → 上下文构建 → LLM 请求 → 解析与配额 → 持久化 → UI/Markdown 导出的完整数据链路；核对失败、截断、重试和部分结果。
- 取消、重复启动、迟到进度事件、项目切换和监听器清理；确认状态更新不会落到错误项目或已结束操作。
- 边界输入和 Windows 路径；包括空目录、忽略规则、路径分隔符、权限失败、超大/异常内容及用户可控配置。
- 用户承诺的题量、界面文案、`shared/types.ts` 中预算和 README 是否一致；共享类型或契约变化要沿实际调用者检查。
- 模型错误与凭证处理；错误消息、日志、事件、结果文件和导出内容不得泄漏 API Key 或其他敏感信息。

只陈述被审查 commit 的实际实现和验证能够证明的保证。涉及持久化加密、原子写入、操作隔离等属性时，先从代码路径和验证证据确认，再描述为已有保证。

## 外部 review 的处理闭环

收到外部 review、自动化 finding 或用户转述的审查意见时，先检查本地代码和真实调用路径，再决定处理方式。逐条归类为**成立、部分成立、不成立或重复**，并简述证据。不要直接照搬 reviewer 提出的方案；先确认根因、责任边界、兼容性与最小可行修复，再选择范围内最合理的处理。

对成立或部分成立的问题，修复并补充针对根因的回归证据；新提交后重新审查相关路径和检查。若不采纳全部或部分建议，说明不采纳理由、证据与剩余风险。对于明确未解决的问题，必须保留可见状态和后续去向；不得静默 resolve 或把未完成项写成已修复。

回复每条外部意见时使用以下字段：

```text
状态：成立 / 部分成立 / 不成立 / 重复；已修复 / 未修复 / 已跟踪
根因：代码路径和触发条件
方案与理由：采取的修复，或不采纳 reviewer 方案的依据
新 commit：处理后的 commit（如有）
验证：命令、回归证据与结果
证据边界：未覆盖部分和剩余风险
后续：未闭环事项的 issue 或明确负责人/计划
```

若意见重复，引用首个对应 finding 或回复并说明重复关系；不能只以“已讨论”关闭一个仍然成立的问题。被接受风险的 P2 也应持续可见，直到后续 issue 完成或风险被明确重新评估。

## PR review 记录格式

每次独立审查以如下结构给出完整结论，省略项写明“不适用”或原因，不用空白暗示通过：

```text
Reviewed commit: <head SHA>
Base: <base branch> @ <base SHA>
结论：Approve / Request changes / Comment
Findings：按严重度列出位置、触发、机制、影响、修复方向和验证；无实质缺陷时明确写无
验证证据与边界：实际命令和结果、人工/外部条件、mock 或 smoke 的覆盖边界
未验证/剩余风险：明确列出，或写无并说明判断范围
```

只在对应 head 上确认没有未解决阻断项且验收证据充分时写 `Approve`。`Comment` 不应被团队记录成“通过”。新提交后更新 Reviewed commit，并重新确认受影响结论。

## 依赖与合并顺序

PR 应链接相关 issue、依赖 PR 和版本依据。若一个变更依赖另一 PR 的接口或行为，应写明必须先合入的依赖，以及依赖未合入时当前验证的限制。并行 PR 合并前重新读取目标分支版本；本分支版本若不再高于目标分支，应先按 [版本管理](VERSIONING.md) 更新并重新验证。审查模板和本文是仓库约定，不会自行启用 GitHub 的强制合并门禁。
