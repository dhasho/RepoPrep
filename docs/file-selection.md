# 上下文文件选择

## Why

旧的统一文件评分会让深层核心实现被路径深度压低；预算裁剪第一个大文件后还会停止遍历，导致后面的源码与模块缺席。现在选择器先做职责与模块覆盖，再结合入口、局部引用等信号排序；预算不足时对已选文件公平分配正文空间。

## Scope

`electron/services/file-selection.ts` 提供纯选择策略，`context-builder.ts` 按原扫描快照探测信号、读取选中文件并组装批次。Coarse 仍排除业务源码；fine 保留原顶层模块分组与最多十个模块批次。扫描结果仍是文件读取的授权来源。

此处的启发来自 [Aider 的 repository map](https://aider.chat/docs/repomap.html)，但实现是轻量局部启发式，不是完整 AST 或语义分析：职责和模块优先于全局热度，同一模块内再结合入口、引用数、路径与角色。JavaScript/TypeScript 支持相对导入解析，Python 支持轻量本地 import 解析；其他语言回退到确定性的模块、角色和路径顺序。不会解析 `tsconfig` 路径别名，也不会发现由动态运行时逻辑加载的依赖。

## Constraints

- 只通过 `readProjectContent` 和原始已批准 scan 读取。项目身份变化仍抛出 boundary error，普通 I/O 错误才按静态分类汇总。
- 每次 `pickFiles` 最多探测 128 个文件、2 MiB。探测内容先脱敏，再用于信号分析；仅在本次调用内缓存脱敏文本。Coarse 探测前先过滤掉业务源码。
- 当所有候选文件的估算内容、渲染开销和读取量能容纳时，不套用 64 文件窗口，选中文件保留全文。预算超限时最多先选 64 项，并为每项预留约 1 KiB，再用 water-fill 将短文件的余量分给尚未饱和的文件。选中文件的额外磁盘读取最多 16 MiB；连同探测的 2 MiB，每次调用磁盘读取总量最多 18 MiB。缓存仅保存本次调用中的脱敏文本，不将其描述成字节级内存上限。读取失败或超限跳过后继续回填后续候选。
- 预算以 JavaScript UTF-16 字符计数，覆盖头部、文件树、路径、标题、围栏、分隔符、脱敏扩张和警告预留。只有实际省略或裁剪时才标记内容截断；读取失败保留独立警告。
- 不新增依赖。

## 验收标准

- 反转扫描文件顺序后选择稳定；manifest 入口和被引用的深层核心源码在探测以外也能通过候选白名单得到排序提升。
- 巨大 README 不会阻止多个源码模块获得内容；普通 medium 项目若完整合计可容纳，README 与其他候选都保留全文。
- Coarse 不探测或包含业务源码；fine 模块分组和上限保持兼容。
- 实际渲染批次不超过各自预算，截断与读取警告对应真实省略、裁剪或读取失败。
- 文件内容只由批准扫描读取，敏感值不会进入信号缓存、批次或模型提示。

## 验证计划

- `npm run test:file-selection`：选择策略与真实扫描/上下文集成用例。
- `npm run test:question-budget`：生成请求预算、警告与既有 fine 行为。
- `npm run typecheck`：Node/Electron 与 Web 严格类型检查。
- 集成用例使用真实 scan、`buildContext`、`renderBatch` 和生成请求，覆盖 2,000 个普通文件与深层被引用核心、超 medium 预算 README 与多个源码模块、Coarse 大 README 与小型清单、超过 128 个文件的近预算渲染、反转 scan 顺序、UTF-16 预算和敏感内容边界。
