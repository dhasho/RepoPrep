# API Key storage and IPC boundary

RepoPrep persists API Keys as versioned ciphertext produced by Electron's asynchronous `safeStorage` API. The ciphertext is stored in `settings.json` and its managed recovery copies; the key is decrypted in the main process only when a generation, explanation, connection test, or model-list request needs it. If the OS credential provider is unavailable, decryption and new secret writes fail closed. Linux `basic_text` and unrecognized backends are not accepted as protected storage.

`settings:get` returns profile metadata, `hasApiKey`, and a credential status. It never returns saved plaintext or ciphertext. A settings save carries a per-profile `keep`, `replace`, or `clear` intent. Probe requests can carry a user-entered replacement key or request a saved key by profile ID. Main verifies that saved-key use targets the canonically equivalent saved endpoint and the same effective protocol; changing either requires replacing or clearing the saved key. An absent protocol is equivalent to `openai` for legacy profiles; `anthropic` uses the Claude Messages format. Renderer claims such as `hasApiKey` are ignored for authorization.

The renderer's password field is empty for stored credentials. The settings page shows whether a key is protected, unavailable through the OS credential store, or waiting for migration, and makes pending replacement and clearing explicit. Clearing a typed replacement on a profile with a saved key returns to `keep`; deleting a saved key always requires the explicit clear action. A key typed for replacement necessarily exists briefly in renderer draft state and the corresponding IPC request. After a confirmed save and authoritative `settings:get` readback, the draft is cleared unless the user changed that key while the request or readback was pending. Saved keys are never read back to populate the field or masked into a reusable value.

Legacy plaintext settings are migrated before a private key is resolved or settings are saved. The migration checks the primary settings file, its managed `.bak` and `.corrupt` copies, and only the store's exact managed temporary-file names. Parseable legacy settings are encrypted. Malformed managed snapshots are retained as an OS-encrypted binary archive with the marker `RepoPrep encrypted settings archive v1`; the marker identifies the format but does not authenticate it, so decryption must succeed before bytes are considered recovered. Archive reads are bounded. If the provider is unavailable or any copy cannot be safely converted, the operation reports migration pending. Each file replacement is atomic, but conversion across several files is not a transaction: a failure may leave a mixture of encrypted and legacy copies. Existing bytes remain recoverable and a later attempt resumes conversion; no success is reported while a managed plaintext key copy remains.

On Windows, Electron `safeStorage` uses Windows DPAPI for the current Windows user. This protects stored bytes from someone who only obtains the settings file, but it does not protect against malware or another process running with the same user access, a compromised application process, or a live renderer request that legitimately asks main to use the credential. OS-backed storage is an at-rest protection boundary, not a defense against compromise of the signed-in account or active session.

Verification uses synthetic keys and temporary directories only. `npm run test:ipc` covers storage migration, recovery, IPC validation, and fake-crypto boundary tests. `npm run test:native-credentials` builds the app and runs the actual `safeStorage` adapter and settings service in Electron against isolated temporary `appData`, `sessionData`, and `userData`; it emits `VERDICT NATIVE-CREDENTIAL-OK` only after save, no-plaintext inspection, public-readback inspection, private-store roundtrip for legacy and Anthropic profiles, and rejection of cross-protocol credential reuse all pass.
